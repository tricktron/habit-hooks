Go Plugin Sensor

golangci-lint findings mapped to coaching smells

Slice 01 · TDD workflow · revised after first failed attempt

User Story

A Go developer enables habit-hooks-go and runs habit-hooks --all against their project. golangci-lint findings are translated into coaching smell blocks they can act on. Unmapped linter rules are dropped silently, not forwarded raw. A missing golangci-lint answers in one line, not a traceback.

Outer Boundary

What this slice touches

  • Plugin package: habit-hooks-go (entry point habit_hooks.plugins → go)
  • Test surface: plugins/go/tests/ with conftest.py putting sensors/ on sys.path
  • Runner: python -m pytest (pyproject.toml created early for uv run pytest)
  • No core changes: all five target smells (high-complexity, oversized-function, unused-variable, unused-import, parse-error) already have catalogue entries and guides in the generic plugin

Shell Boundaries

CLI

Sensor helper: golangci_lint_sensor.py underscore

The filename must use an underscore, not a hyphen. Python cannot import golangci-lint_sensor.py as a module — conftest.py puts sensors/ on sys.path and imports from golangci_lint_sensor import main. Every sibling sensor uses underscore (ruff_sensor.py, pmd_sensor.py).

Filesystem

Bundled fallback config: .golangci.yml stripped from maratori/golangci-lint-config. The sensor passes --config ${dir}/.golangci.yml only when the project has no config of its own — a project's own config always wins.

Functional Core

The sensor helper is a loose script (${python} ${dir}/golangci_lint_sensor.py), so its own directory is sys.path[0] and neighbours are plain top-level imports — from tool_spawn import run_tool, never a package-relative import.

Pipeline

  1. Split argv: everything after -- is the file list
  2. Config check: does the project have its own .golangci.yml / .golangci.yaml / golangci.yml? If yes, pass nothing. If no, pass --config ${dir}/.golangci.yml
  3. Run golangci-lint via tool_spawn.run_tool (byte-identical copy of the other four Python plugins' tool_spawn.py)
  4. Parse JSON: json.loads(stdout) — each entry is one issue
  5. Map via routing table: linter + text prefix → smell
  6. Group by smell, sort alphabetically (same as ruff's findings())
  7. Emit: json.dumps(findings) on stdout, exit 0

Smell routing table

gocyclo(any)high-complexityforward

Unmapped linters are dropped — the same "a sensor emits vocabulary smells only" rule ruff and knip follow. A key nobody catalogued has no guide and no severity, so forwarding it can only fail a run and decline to explain why.

Acceptance Criterion

Given-When-Then

Given a Go project with go.mod and a function whose cyclomatic complexity exceeds golangci-lint's threshold,

When habit-hooks --all runs,

Then the output contains a high-complexity coaching block with the file path and line number,

And unmapped findings (e.g. unused on a non-variable) do not appear in the output at all.

Test List

The codebase has exactly three test strategies. Stubbing an internal run_tool function is not one of them and was the primary mistake in the first attempt.

Lesson: no run_tool stubbing. No test anywhere in the codebase (95 test files across all plugins) stubs an internal function. The main() orchestration (run tool → parse → map → emit) is implicitly tested by real-tool tests that spawn the sensor as a subprocess. Pure logic is tested by calling findings(), issues(), or golangci_lint_crashed() directly with synthetic data dicts — no tool involved.

Pure function tests synthetic data

File: test_the_golangci_lint_pipeline_maps_findings_to_smells.py

Calls findings(entries) with hand-built golangci-lint-JSON-shaped dicts. No tool involved. Mirrors ruff's test_the_ruff_pipeline_maps_codes_to_smells.py.

  • Zero issues → findings([]) returns [] — walking skeleton
  • Simple linter routing (parametrized): gocyclo→high-complexity, funlen→oversized-function, ineffassign→unused-variable
  • unused with "var " prefix → unused-variable
  • unused with "func " prefix → dropped
  • typecheck with "imported and not used" → unused-import
  • typecheck with other text → parse-error
  • Multiple findings grouped by smell, sorted alphabetically
  • Exit code 0 and 1 trusted; 2/127 → crash (parametrized, pure golangci_lint_crashed())

Real-tool tests subprocess + real golangci-lint

File: test_the_golangci_lint_sensor_runs_the_real_tool.py

Spawns the sensor via subprocess.run([sys.executable, str(SENSOR), ...]). Mirrors ruff's test_the_ruff_sensor_runs_the_real_tool.py.

  • Real tool on a clean file → []
  • Real tool on a file with violations → mapped smells in output

Crash test pure function

File: test_a_crashing_golangci_lint_fails_the_run.py

Exercises golangci_lint_crashed() directly with synthetic CompletedProcess objects. Mirrors ruff's test_a_crashing_ruff_fails_the_run.py.

  • Exit 0 and 1 → False (parametrized)
  • Exit 2, 127, -9 → True (parametrized)

Missing-tool test universal pattern

File: test_a_golangci_lint_nobody_installed_is_named.py

env={"PATH": "/nonexistent"}, assert "golangci-lint: command not found". Mirrors ruff's test_a_ruff_nobody_installed_is_named.py. Universal across all plugins.

  • Missing tool (PATH=/nonexistent) → exit 2, "golangci-lint: command not found"

Config tests filesystem

File: test_the_go_files_leave_vendor_alone.py

  • Project with own .golangci.yml → sensor does not pass --config
  • Project without config → sensor passes --config ${dir}/.golangci.yml

Vendored test python -S gate

File: test_a_vendored_sensor_finds_its_neighbour.py

Copies sensor files into .habit-hooks/go/sensors/, runs with python -S to deny site-packages. The sensor imports tool_spawn from beside itself — must resolve without the package installed. Mirrors java's test_a_vendored_sensor_finds_its_neighbour.py.

  • Vendored sensor finds its neighbour (tool_spawn) — python -S gate

Test Conventions

  • Bare asserts — no custom messages. Universal across 95 test files.
  • Module docstring carries the "why". No inline comments in test body.
  • _-prefixed helper builders for setup data (like ruff's _entry())
  • Descriptive function names are the spec — test_zero_issues_is_no_findings, not test_01
  • Parameter named entries, not issues — avoids shadowing the module-level issues() function

Sensor spec

# sensors/golangci-lint.toml
argv = ["${python}", "${dir}/golangci_lint_sensor.py", "${args}", "--", "${files}"]

Note the underscore in golangci_lint_sensor.py — must match the actual filename. The ${args} placeholder is where --config (or nothing) is expanded.

Decision Context

Why these choices

Underscore filename

golangci_lint_sensor.py, not golangci-lint_sensor.py. Python cannot import a hyphenated filename. The conftest puts sensors/ on sys.path and imports from golangci_lint_sensor import main. Every sibling sensor uses underscore. The sensor spec toml must spell the same filename.

Three test strategies, not four

Pure function tests (synthetic dicts), real-tool tests (subprocess), and missing-tool tests (PATH=/nonexistent). There is no "stub the internal run_tool and test main()" strategy anywhere in the codebase. The main() orchestration is implicitly tested by real-tool tests that spawn the sensor as a subprocess.

Walking skeleton is findings([])

The first test is test_zero_issues_is_no_findings calling findings([]) directly — not a main() orchestration test with a stubbed run_tool. This is how ruff's test_zero_entries_is_no_findings works.

Routing by linter + text prefix

golangci-lint's JSON gives linter and text per issue. unused and typecheck are ambiguous without the text: unused with "var " is unused-variable, with "func " it is dropped; typecheck with "imported and not used" is unused-import, otherwise parse-error. The other three (gocyclo, funlen, ineffassign) map unambiguously.

tool_spawn.py is a byte-identical copy

Every Python plugin (generic, java, php, python) ships its own copy. None may import habit-hooks or each other (dependencies = []), so a helper cannot reach a shared implementation. The gate test_every_plugin_carries_the_same_copy keeps them from drifting.

All five target smells already exist

high-complexity, oversized-function, unused-variable, unused-import, and parse-error all have catalogue entries (enforced) and guides in the generic plugin. No new smells, no new guides, no core changes.

Bundled config from maratori

Stripped from maratori/golangci-lint-config — enables only the linters this plugin maps. A project's own .golangci.yml always wins; the bundled one is the fallback for "this project has none."
