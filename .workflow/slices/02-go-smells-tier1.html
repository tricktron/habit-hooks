# SMELL_BY_LINTER — add errcheck (govet needs text routing, see below)
SMELL_BY_LINTER = {
    "gocyclo": "high-complexity",
    "funlen": "oversized-function",
    "ineffassign": "unused-variable",
    "errcheck": "unchecked-error",          # NEW
}

def smell_of(linter: str, text: str) -> str | None:
    if linter in SMELL_BY_LINTER:
        return SMELL_BY_LINTER[linter]
    if linter == "unused":
        return "unused-variable" if text.startswith("var ") else linter
    if linter == "typecheck":
        return "unused-import" if "imported and not used" in text else "parse-error"
    if linter == "govet":                   # NEW
        if "copies lock value" in text or "passes lock value" in text:
            return "copied-lock"
        return "govet"                      # other govet analyzers: forwarded
    return linter

Guides

plugins/go/src/habit_hooks_go/guides/unchecked-error.md NEW

Incorporates Dave Cheney's "Don't just check errors, handle them gracefully" and learn-go-with-tests's "Unchecked errors" section.

An error you didn't check is a failure you didn't notice. Go returns
errors as values — the compiler won't force you to read them, so the
discipline is yours. Assign the error, check it, and decide what to do
with it.

Work through it in order:

1. **Check before you use the result.** A function returning `(T, error)`
   expects you to test `err` before touching `T`. The unchecked path is the
   one where `T` is zero-valued, nil, or stale — using it silently is the
   bug, and it surfaces at the worst moment: a nil dereference in
   production, an empty config loaded without complaint, a file that
   "wrote" to a closed handle.
2. **Handle it, don't just pass it on.** Bare `return err` propagates the
   error but loses where it happened. Add context at each layer with
   `fmt.Errorf("doing X: %w", err)` — the `%w` verb preserves the chain so
   `errors.Is` and `errors.As` still work upstream. A caller six frames up
   should read "could not read config: open failed: no such file or
   directory", not just "no such file or directory".
3. **Handle it once.** Logging the error *and* returning it is handling it
   twice — the log fills with duplicate lines and the top-level caller gets
   a stripped error. Either wrap it and return it, or log it and stop. Not
   both.
4. **Prefer opaque errors.** Return the error with added context rather
   than inspecting its type or value. If a caller needs to distinguish
   error kinds, assert behaviour — an interface like `Temporary() bool` —
   not a sentinel value (`== ErrFoo`) or a type assertion
   (`err.(*MyError)`). Comparing `err.Error()` to a string is a code
   smell: the message is for humans, not for program logic, and a
   reworded message silently breaks the check.

Suppressing the warning with `_ =` or a blank assignment hides the
question instead of answering it. If the error genuinely cannot occur, a
comment saying so is cheaper than a silent discard that masks the one
time it does.

plugins/go/src/habit_hooks_go/guides/copied-lock.md NEW

Grounded in learn-go-with-tests sync chapter ("A Mutex must not be copied after first use") and the go vet copylocks analyzer.

A mutex copied is a lock broken. Go copies values on every assignment
and function call, and `sync.Mutex` documents "must not be copied after
first use" — the copy's lock state is undefined, and the original's
protection is silently gone. Two goroutines can enter the critical section
through what they think is the same lock but are actually two.

The fix is a pointer. Pass `*Counter`, not `Counter`. If the struct lives
in a receiver, use a pointer receiver. If callers construct the value,
give them a constructor (`NewCounter()`) so they receive a pointer from
the start and never have the chance to copy by value.

`go vet` catches this — do not silence it. A `go vet` pass on a struct
containing a mutex is not a suggestion, it is a bug report.

Decision Context

Problem

The Go plugin enables errcheck and govet in its bundled .golangci.yml, but their findings fall through to return linter (golangci_lint_sensor.py:58) and render through uncoached.md — a generic "ask yourself why the rule exists" prompt with zero Go context. The study shows dedicated coaching prompts dramatically outperform generic ones. errcheck is the canonical Go mistake that learn-go-with-tests dedicates an entire section to.

Chosen approach

Introduce two Go-specific catalogue smells (unchecked-error, copied-lock) with dedicated guides in the Go plugin. This converts the implicit functional coupling (sensor forwards raw linter name → uncoached.md assumes it knows what the linter means) into contract coupling (sensor maps to an explicit smell key → guide provides Go-specific coaching). The guide resolution infrastructure already supports this — plugins_for_language puts the Go plugin first.

Alternatives considered

  • Map errcheck → swallowed-exception — rejected. Go has no exceptions; the error is a return value never acknowledged, not an exception caught and suppressed. The mechanism, hazard, and fix are structurally different (see Tier 1 analysis table).
  • Keep forwarding, improve uncoached.md — rejected. A generic guide cannot provide Go-specific coaching (pointer receivers, %w wrapping, opaque errors) without being wrong for other languages.
  • Drop errcheck/govet from .golangci.yml — rejected. The "ship it forwards, coach it later" stance is by design (confirmed in Phase 2). Removing the linters would create false-clean runs.

Constraints

  • dependencies = [] — the Go plugin cannot import the core or other plugins. Guides are resolved by filename through the override chain, not by imports.
  • govet is a multi-analyzer linter — text-based routing is required, same as unused/typecheck. The copylocks analyzer's text contains "copies lock value" or "passes lock value".
  • The str | None return type on smell_of and the if smell is None: continue guard in findings() are dead code (no path returns None) — leftovers from the abandoned "drop" design. Left as-is to keep this slice focused; the docs fix reconciles the design rationale, not the type signature.

Dave Cheney error handling practices in the guide

The unchecked-error.md guide weaves in four practices from "Don't just check errors, handle them gracefully":

  1. Handle it, don't just pass it on — add context with fmt.Errorf("...: %w", err) at each layer
  2. Handle it once — don't both log and return (duplicate log lines, stripped error at top level)
  3. Prefer opaque errors — return with context, don't inspect type or value
  4. Assert behaviour, not type — use interfaces (Temporary() bool), not sentinel values or type assertions; never inspect err.Error() string
